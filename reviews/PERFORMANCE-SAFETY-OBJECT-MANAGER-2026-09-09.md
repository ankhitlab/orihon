# Ревью Orihon: производительность, безопасность, ИИ и ObjectManager

Дата: 9 сентября 2026. Версия package.json: 2.0.1. Проверена текущая рабочая копия с уже существовавшими незакоммиченными изменениями. Исходники библиотеки в рамках ревью не исправлялись.

## Вывод

Главный резерв — обеспечить последовательную обработку изменений от хранилища до рендера. Сейчас инкрементальность есть на отдельных участках, но теряется между ними: движок ИИ копирует коллекцию, менеджер повторно нормализует объекты, пакетный режим не охватывает все изменения, сцена пересоздаёт полные наборы для слоёв. Ускорять вычислительные ядра до исправления этих путей преждевременно.

Предположение о недоиспользованном менеджере подтверждается: инфраструктура dirty flags не подключена к обновлению сцены; пространственный индекс используется для точечных маркеров, но не для предварительного отбора декораций; ObjectManager.queryHit не является стандартным маршрутом map.query. При этом несколько представлений объектов уже рассинхронизируются.

## Находки

### 1. P1 — Обновление свойств оставляет старый объект в пространственном индексе

Место: `src/services/object-manager.ts:1097–1100`, потребители `:2302–2306`, `:1825`.

**Воспроизведено.** После add(a, title=old), update(a, title=new) при прежних координатах `getObject(a)` возвращает new, а `index.get(a).value` — old. Ветка property-only обновляет items и scene, но не SpatialRecord.value. DOM-перерисовка читает record.value; пространственный предикат также получает старые свойства. Получаются разные данные для popup, стиля и фильтрации.

Исправление: единый commit объекта обновляет все представления; для неизменной геометрии достаточно заменить value существующей записи без перемещения между ячейками. Отдельно инвалидировать маску фильтра/кластеров и временной видимости, если изменились их входные свойства: сейчас property-only не сбрасывает эти кэши.

### 2. P1 — GPU-обновление молча теряет остаток пакета при смене типа геометрии

Место: `src/services/object-manager.ts:988–995`.

**Воспроизведено.** Когда доступен patch-путь, update([a→LineString, b→новая точка]) записывает a, затем выходит из всего метода. b остаётся старым. Аналогичный выход возможен на невалидной геометрии. Возвращается обычный this без сообщения о частичном применении.

Исправление: заранее классифицировать весь пакет; при изменении топологии применять весь пакет общим путём либо продолжать обработку и выполнить одну итоговую перестройку. Проверить также частично мутирующие «пробные» пути property-only и animated: они меняют префикс списка до решения, подходит ли быстрый путь.

### 3. P1 — points.replace фактически добавляет точки вместо замены коллекции

Место: `src/ai/engine.ts:361–383`; проекция `src/ai/projection.ts:267–281`.

**Воспроизведено.** Без clearMap:true повторная команда с тем же id возвращает DUPLICATE_ID. Если новые id другие, старые остаются в движке. Проекция при этом вызывает source.replace(features) и оставляет только новый набор. После восстановления snapshot старые точки снова появятся.

Исправление: для points.replace начинать новую Map соответствующей коллекции независимо от clearMap; clearMap должен отдельно управлять очисткой остальных коллекций и сцены. Это особенно существенно для повторных инструкций пользователя ИИ.

### 4. P1 — Отмена ИИ-агента не останавливает оставшиеся инструменты текущего ответа

Место: `src/ai/agent.ts:141–147`, `:168–175`.

**Воспроизведено.** Адаптер возвращает два вызова; первый отменяет AbortController, второй всё равно выполняется. Проверка abort стоит только перед запросом следующего ответа модели. Передача signal инструменту не заменяет проверку в оркестраторе: синхронный инструмент может не обрабатывать его.

Исправление: проверять отмену сразу после complete и перед каждым execute; не превращать отмену в обычный tool-result с продолжением серии. Дополнительно нужен лимит числа инструментов на ответ/запуск: maxTurns ограничивает ответы модели, а не число операций внутри ответа.

### 5. P1 — Маленькая команда ИИ глубоко копирует всю коллекцию

Место: `src/ai/engine.ts:361–362`, `:120–132`, `:496–502`, `:220–235`; `src/ai/runtime.ts:273`.

**Воспроизведено измерением.** Для обновления одного объекта N+3 вызова JSON.stringify. Получение компактного контекста — N+4: getSnapshot сначала копирует объекты по одному, затем повторно весь snapshot. Компактный результат для модели не означает дешёвое его построение.

| Объектов | update одного объекта | Сериализаций | getContext | Сериализаций |
| ---: | ---: | ---: | ---: | ---: |
| 1 000 | 1,50 мс | 1 003 | 2,50 мс | 1 004 |
| 10 000 | 13,08 мс | 10 003 | 19,16 мс | 10 004 |
| 50 000 | 76,27 мс | 50 003 | 116,93 мс | 50 004 |

Это один диагностический прогон Node 24 с подсчётом вызовов, не стабильный бенчмарк. Надёжный вывод — линейная зависимость и число копирований; абсолютное время зависит от окружения.

Транзакция дополнительно копирует все коллекции при fork и commit. При нескольких командах событие несёт полный snapshot, а проекция вызывает applySnapshot с source.replace, теряя инкрементальность даже для неизменённых коллекций (`projection.ts:249–263`).

Исправление: хранить внутренние неизменяемые объекты, копировать только изменяемые ветки; начать хотя бы с поверхностной Map вместо clone каждого feature. Для replace/clear не копировать старую коллекцию вообще. Контекст строить из счётчиков/агрегатов и ограниченной выборки id. Дельты многошаговой транзакции применять атомарным batch; snapshot использовать для восстановления. Не убирать изоляцию внешних объектов ради скорости.

### 6. P2 — beginBulk не охватывает update и remove

Место: `src/services/object-manager.ts:899–913`, `:1060–1061`, `:1185–1186`, быстрые пути `:1103–1111`, `:1024–1026`.

**Воспроизведено.** beginBulk → перемещение → remove → endBulk даёт три инвалидации layout вместо одной. В быстрых путях возможны непосредственные render/syncSceneLayers внутри bulk. RAF склеивает часть отложенных render, но не отменяет уже выполненные сбросы, прямую синхронизацию и GPU draw. Это затрагивает и FeatureSource.batch через #applySourceChange.

Исправление: общий журнал изменений и единая flush-функция. При bulk>0 разрешать обновление хранилища, накапливать dirty ids/типы изменений, отложить layout, scene sync, draw до внешнего endBulk. Пустой endBulk также не должен сбрасывать layout.

### 7. P2 — update создаёт неизвестные объекты в обход maxObjects

Место: `src/services/object-manager.ts:793`, `:1036–1040` (также GPU-ветка `:981`).

**Воспроизведено.** maxObjects:1, add(a), update(b) → два объекта. Метод описан как обновление существующих объектов, но общий путь делает items.set без проверки существования и лимита. На GPU новый id может дополнительно не получить слот до перестройки.

Исправление: update отклоняет неизвестный id; если нужен upsert — отдельный явный контракт с общим контролем размера. Текущий maxObjects документирован как ограничение add, поэтому это не следует выдавать за нарушение обещанной глобальной квоты; однако использовать его как защиту памяти сейчас нельзя.

### 8. P2 — JSON-валидатор меняет прототип входных properties

Место: `src/ai/engine-validation.ts:74–80`, использование `:128–129`.

**Воспроизведено.** JSON properties с собственным ключом __proto__ записывается в обычный {} через result[key]=… . Ключ становится прототипом: в результате properties.alert может быть true без собственного alert; сам __proto__ исчезает из собственных ключей. Следующая JSON-копия теряет эти данные.

Глобальный Object.prototype в проверке не изменился. Это локальная подмена прототипа и нарушение JSON-семантики, а не доказанная глобальная prototype pollution или исполнение кода.

Исправление: создавать словари через Object.create(null) либо определять собственные data properties; применять тот же принцип ко всем построителям словарей из внешних ключей. Не полагаться на `in` для проверки наличия обязательного собственного поля.

### 9. P2 — Dirty flags не потребляются, сцена перестраивается целиком

Место: `src/services/object-scene.ts:248–255`; `src/services/object-manager.ts:3665–3828`.

**Статический анализ.** consumeDirty объявлен, но в src нет его вызовов. Флаги накапливаются по живым id до remove/clear. При включённых декорациях #syncSceneLayers проходит все items, разрешает стили, формирует новые массивы символов/линий/полигонов и вызывает setPaths/setPolygons. Даже hover/selection через #afterVisualStateChange может привести к полной синхронизации.

Для точек viewportBBox вообще не используется перед построением иконок/подписей; для линий и полигонов проверка bbox есть, но уже после разрешения стиля. Пространственная инфраструктура менеджера не сокращает этот обход.

Исправление: consumeDirty использовать как журнал частичных обновлений, разделить position/style/topology/visibility. Ввести bbox-индекс для протяжённых геометрий и отбор точек видимого окна с запасом для иконок/подписей. Существующий индекс по одной опорной точке нельзя без изменения использовать для всех полигонов: можно пропустить фигуру, пересекающую окно при невидимой опорной точке.

### 10. P2 — Вычисления коллизий иконок и подписей выбрасываются

Место: `src/services/object-manager.ts:3699–3780`, `:3833`.

**Статический анализ.** labelCandidates наполняется экранными прямоугольниками иконок и подписей, но завершается `void labelCandidates`. В scene.redrawLabels выполняется собственная компоновка подписей, а подготовленные здесь препятствия-иконки не передаются. Это и лишние проекции/аллокации, и незавершённая общая компоновка.

Исправление: один проход collision layout для иконок и подписей с использованием результата обоими рендерами; либо убрать вычисление неиспользуемых кандидатов до появления этой функции.

### 11. P2 — SSE накапливает неограниченную очередь для медленного клиента

Место: `src/ai/http.ts:159–170`.

**Статический анализ.** На каждую мутацию выполняется сериализация события и controller.enqueue без проверки desiredSize, предела очереди или политики отставания. При частых обновлениях и подключённом медленном читателе память удерживает очередь; multi-command transaction может содержать большой snapshot. Abort/cancel освобождает подписку, но не ограничивает живое медленное соединение.

Исправление: ограниченная очередь по байтам/событиям, при превышении — закрыть поток с требованием snapshot-resync. Нельзя молча выкидывать дельты при проверке последовательных revision. Авторизация и rate limits документированно находятся на стороне host; отсутствие встроенного login здесь само по себе не дефект.

## Где проходит граница между полезным разделением и дублированием

| Компонент | Сохранить ответственность | Что изменить |
| --- | --- | --- |
| FeatureSource | Канонические feature и versioned batch | Общий источник изменений; не дублировать алгоритм diff в каждом потребителе |
| ObjectManager | Индексы, состояние выбора, фильтры, маршрутизация рендера | Один commit/flush, частичное обновление derived-представлений |
| ObjectSceneController | Иконки, подписи, движения, линии, полигоны | Потреблять dirty flags, не пересобирать всю сцену на любой сигнал |
| RemoteObjectManager | Загрузка окна, отмена, debounce | При стабильных id применять diff вместо безусловного clear+add |
| AICommandEngine | Headless-состояние, валидация, ревизии, транзакции | Copy-on-write и дельты; не переносить владение состоянием в браузерный менеджер |
| MarkerCollection / GeoJSON | Простые и независимые способы отрисовки | Общие низкоуровневые утилиты; не заставлять малые наборы оплачивать весь ObjectManager |

RemoteObjectManager (`src/services/remote-object-manager.ts:154–155`) при replace сначала clear, затем add: исчезают selection/state/trails, повторяется ingest, удаляются рендеры даже для неизменённых id. Это соответствует текущему режиму полной замены, но является конкретным резервом: добавить режим reconcile с явной политикой сохранения состояния и сравнением версии/полей.

ObjectManager.queryHit (`:1627`) уже умеет возвращать доменный object id и feature поверх разных рендеров, однако addTo (`:664`) регистрирует слушателей, а не менеджер в map.layers. map.query (`src/map.ts:945`) по умолчанию обходит дочерние слои, поэтому этот адаптер не становится единым публичным путём. Нужен реестр query-provider либо отображение layer-hit→owner-object с исключением повторного обхода дочерних слоёв. Это архитектурный пробел, не утверждение о наличии двойного hit-test во всех текущих вызовах.

Повторная нормализация: property-only сначала вызывает tryNormalizeManagedGeometry, затем #ingestObject вызывает её снова. Если неподходящий объект обнаружен в середине списка, префикс уже изменён и повторно проходит общий путь. Классификация без мутации и передача готовой нормализованной геометрии уберут повторную работу и упростят корректность.

## Безопасность и дальнейшее взаимодействие с ИИ

Положительные механизмы: валидируемые декларативные команды, проверки revision, ограничения групп capabilities, явные AbortSignal, безопасный текстовый путь popup. Ключ модели задаётся host-адаптеру; само наличие apiKey в опциях не доказывает утечку. Для production-хоста отдельно нужны проверенные правила доступа к engine/session и ограничения размера входа; библиотека прямо делегирует это приложению.

Для масштабного ИИ-сценария полезен серверный query API: фильтр/bbox/search, ограниченная выдача полей, limit/cursor и агрегаты. Сейчас компактный getContext полезен модели, но слишком дорого вычисляется. Объектные свойства из внешних данных должны оставаться данными при передаче модели; system prompt не заменяет ограничения инструментов и политику host. Новое API запросов должно работать headless, а браузерные действия focus/select/popup — через менеджер по стабильным collection+id.

## Порядок работ

1. Исправить потерю пакета, points.replace, согласованность индекса и отмену ИИ; превратить диагностические probes в регрессионные тесты правильного поведения.
2. Объединить commit/flush для add/update/remove/bulk, исключить повторный ingest; определить update/upsert и квоты.
3. Подключить dirty flags и частичные обновления scene, завершить общую компоновку; измерять число style calls, нормализаций и GPU uploads на 1/100/1000 изменённых id.
4. Убрать полные JSON-копии ИИ, отдельный дешёвый context, транзакционные дельты. Проверять число сериализаций и размер события, а не только токены ответа модели.
5. Добавить reconcile для remote, owner-aware query, лимиты SSE. Затем браузерный профиль 10k/100k/1M, отдельно plain points и сцена с подписями/линиями.

Не объединять всё в один большой класс: полезен общий протокол изменений и идентификаторов при сохранении headless-движка и специализированных рендереров.
